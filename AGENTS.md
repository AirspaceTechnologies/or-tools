# AGENTS.md

The single source of truth for this repo's architecture, invariants, and
conventions. This is a fork of [google/or-tools](https://github.com/google/or-tools)
that adds Go bindings (SWIG-generated) and publishes prebuilt binary tarballs for
Airspace's Go services. This root file covers what is airspace-specific, what breaks
during upstream merges, and how releases work; human-oriented install/build steps
live in `AIRSPACE-README.md`. No scoped `<dir>/AGENTS.md` files exist yet; if the
release tooling or Go binding layer accumulates its own non-obvious detail, scope it
there.

> Facts below verified against the `airspace` branch at tag `v9.12-go1.24.3`
> (2026-07-20). Line numbers cited are as of that tag and will drift after merges.

## Maintaining AGENTS.md files

Treat this file as code: when a change makes a documented statement wrong, update it
in the same task. Keep it describing what is non-obvious and true now (invariants,
gotchas, conventions), not a restatement of what the code already makes plain.
Concrete claims (names, paths, cited line references) must match the repo. Delete
statements that become false rather than letting them rot.

## Invariants (never violate)

- **This is a PUBLIC fork.** Never reference internal Airspace services, repo
  names, images, infrastructure, or service architecture anywhere that gets
  committed or pushed: docs, code comments, commit messages, PR descriptions,
  release notes. Describe consumers generically (see "Who consumes this repo");
  the specifics live in internal runbooks. Working context you were given (plans,
  internal docs, Slack) may name internal systems: do not copy those names into
  this repo.
- No hardcoded secrets, tokens, or keys.

## Who consumes this repo

- Downstream Go services consume the bindings as a Go module
  (`github.com/airspacetechnologies/or-tools/go/ortools`), pinned by pseudo-version
  to a commit on `airspace`, and link the shared libs via CGO. **The module commit
  and the installed shared-lib version must match**: the wrappers and
  `libgoortools` are generated from the same tree.
- The Linux tarballs from this repo's GitHub releases get installed to
  `/usr/local/lib` in consumers' build/runtime images; Mac developers install the
  macOS tarball the same way for native builds (steps in `AIRSPACE-README.md`).

**Coordination rule:** publishing a new release is only half the job; downstream
images and module pins must be updated together. The specifics live in internal
runbooks and are intentionally not documented in this public fork.

## Branch & remote model

- `origin` = `AirspaceTechnologies/or-tools`, `upstream` = `google/or-tools`.
- `stable` mirrors `upstream/stable` (merge commits only; no airspace work here).
- `airspace` = `stable` + all airspace patches. This is the default/release branch.
- Merge flow: fetch upstream → merge `upstream/stable` into `stable` → push → merge
  `stable` into `airspace` → resolve conflicts (checklist below) → push → release.

## Version plumbing (do not hand-edit versions)

- `Version.txt` holds MAJOR/MINOR only. PATCH is computed:
  `git rev-list --count v$(MAJOR).0..HEAD` (see `makefiles/Makefile.port.mk`,
  `OR_TOOLS_PATCH`), so it auto-increments with every commit; never hardcode it.
- Tarball name: `or-tools_$(CPU)_$(PORT)_go_v$(OR_TOOLS_VERSION).tar.gz` built in
  `makefiles/Makefile.port.mk` (`INSTALL_GO_NAME`, ~line 327 at v9.12).
  `CPU = uname -m`; `PORT` = `lsb_release` distro-version on Linux (hence
  `CentOS-7.9.2009` from manylinux2014 containers) or `macOS-<sw_vers>` on Mac.
  Naming is fully automatic per build environment; scripts read it via
  `make print-INSTALL_GO_NAME`.
- Release tags follow `v<MAJOR>.<MINOR>-go<GO_VERSION>` (e.g. `v9.12-go1.24.3`).
- `go/ortools/go.mod` is GENERATED by `cmake/go.cmake` (`go mod init` + `tidy`) from
  whatever Go toolchain runs the build. Don't hand-edit; bump Go by changing the
  toolchain in the release Dockerfiles / build host.

## What a release tarball contains

Only the compiled shared libraries: `lib/libgoortools.*` and `lib/libortools.*`
plus version symlinks (packed by `native.sh` from the CMake build dir). No headers,
no `.go` files, no dependency libs: third-party deps (protobuf, abseil, ...) are
**statically linked into** those libs via the airspace patch in
`cmake/dependencies/CMakeLists.txt` (commit `8c706cc426`). The generated Go wrapper
and `.pb.go` sources are committed to the repo `go/` tree (refreshed by `native.sh`),
which is what consumers import as a Go module.

## Build tooling map

| Script | Purpose |
|---|---|
| `native.sh` | Native build + tarball for the host (`--fast` skips CMake regen). Arch-agnostic: everything keys off `uname -m`. |
| `arm.sh` | Mac arm64 cross-compile from an x86_64 Mac host (wraps `tools/cross_compile.sh`). |
| `universal.sh` | `lipo` two Mac tarballs (`-a` arm64, `-x` x86_64) into one universal tarball (`-o`). |
| `tools/release/build_delivery_airspace.sh` | Linux delivery via Docker (~45 min): builds `tools/release/amd64_airspace.Dockerfile` (env → devel → delivery stages; delivery runs `native.sh` in-container) and copies tarballs to `export/`. |

Everything else under `tools/release/` (`build_delivery_linux.sh`,
`*_manylinux_*.sh`, `amd64.Dockerfile`, `arm64.Dockerfile`, publish/test scripts,
encrypted secrets) is **upstream's tooling, unused** by the airspace flow, but
useful as reference (upstream's `arm64.Dockerfile` shows the manylinux_2_28_aarch64
setup).

## Airspace patches that MUST survive upstream merges

Use this as the conflict-resolution checklist when merging `stable` into `airspace`:

1. **Static-link toggles** in `cmake/dependencies/CMakeLists.txt`
   (`8c706cc426`): `BUILD_SHARED_LIBS OFF` and `protobuf_BUILD_SHARED_LIBS OFF` in
   the dependency-fetch block. High conflict likelihood; re-apply if upstream churns
   this file.
2. **Proto `go_package` options** pointing at
   `github.com/airspacetechnologies/or-tools/...` in 7 `.proto` files under
   `ortools/constraint_solver`, `ortools/sat`, `ortools/util`. Conflicts wherever
   upstream edits those option lines.
3. **The entire Go binding subsystem** (airspace-only, upstream has no Go support):
   `cmake/go.cmake` (module path, install-path/rpath logic for Mac at
   `/usr/local/lib`), `ortools/*/go/` SWIG interface files, and the generated-source
   copy steps in `native.sh`.
4. **Go feature patches** on the SWIG layer: `AtSolutionCallback` support, VRP route
   validation, `std::vector<int>` typemap fixes, CPDPTW Go example.
5. `AIRSPACE-README.md`, `AGENTS.md`, `CLAUDE.md`, the `*airspace*` release scripts,
   and `Version.txt` (ours; keep on merge).

After any merge: rebuild natively and run the Go tests before cutting a release;
SWIG/CMake floor bumps upstream are the usual breakage source.

## Verification checklist (any release)

- `file` each tarball's `libgoortools.*` / `libortools.*`: correct arch
  (x86-64 / aarch64 / Mach-O universal). `lipo -info` for the Mac universal libs.
- No external dependency libs required: inspect with `ldd` (Linux) /
  `otool -L` (Mac); only system libs + libortools should appear (static-link patch
  intact).
- Install locally per `AIRSPACE-README.md` and run the Go tests; then run
  downstream consumers' test suites against the new module pin + installed libs
  (`go clean --modcache` first after swapping libs).

## Gotchas

- Intel Mac hosts: the Linux aarch64 delivery build runs under QEMU/binfmt (hours,
  not ~45 min); prefer an arm64 host (M-series Mac, arm CI runner) when available.
- `go clean --modcache` after changing installed or-tools libs; stale module cache
  causes confusing CGO link errors.
- The delivery Dockerfile `COPY . /root/or-tools` builds your working tree, not a
  fresh clone: commit (or at least be aware of) local changes before building.
- Docker layer cache can mask Dockerfile edits to early stages; the build script
  removes prior images, but when iterating manually use `--no-cache` on the env
  stage if tool versions change.
- The committed `go/` tree is largely generated output (refreshed by `native.sh`
  from SWIG/protoc); the hand-maintained sources are the SWIG interface files under
  `ortools/*/go/`. Never hand-edit generated files.
